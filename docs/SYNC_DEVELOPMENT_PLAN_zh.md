## 产品边界

| 领域 | 应有行为 |
| --- | --- |
| 桌面主程序 | 保持 AnySynListen 独立数据目录、应用名和协议，不覆盖官方 AnyListen |
| 账号登录 | 主程序内嵌官方页面登录，网易云→QQ→酷狗；登录验证和歌单拉取分开报告 |
| 账号镜像 | 网易云/QQ/酷狗私人歌单、我喜欢、每日推荐只读；删除镜像只做持续隐藏，永不删除平台原始数据 |
| 左侧歌单 | Ctrl/Shift 整张歌单多选，批量归档、删除；不重做已有的歌单内部单曲多选 |
| 当前日推 | 重新请求来源，当天同一张动态歌单更新；刷新一次不新建一张历史 |
| 历史日推 | 默认自动识别和归档，避免侧栏堆积；不能把普通歌单误判为日推 |
| 原生 WebDAV | 继续使用 AnySynListen 原来的快照协议，与 LX-N 协议隔离 |
| LX-N WebDAV | 默认只读，手动开启双向回写。首次由 WebDAV 来源建立初始状态 |
| LX 冲突 | **只在 LX-N 完整歌单库内**，按最后成功提交的整个歌单库覆盖，包含试听、我喜欢和自建歌单 |
| LX 删除 | 双向开启后，删除传播；LX 手机删除的历史日推在 PC 已归档也须移除 |
| 兼容性 | **不修改 LX-N Music 安卓端**；若手机操作队列自动合并与整库覆盖不一致，应如实报告限制 |
| 交互安全 | 不增加危险操作确认，不自动创建恢复备份；数据失败检验仍必须执行 |
| 用户反馈 | 显示同步中、成功、失败、等待重试；账号登录成功不等于歌单拉取成功 |

## 阶段一：验证原生平台登录（最高优先）

1. 用已存在的 Windows 测试 EXE 启动独立 AnySynListen，先核对设置 UI、三个登录入口与应用数据目录。
2. 网易云：内部 BrowserWindow 完成真实认证、读取专属会话并验证账号 ID；之后读取私人歌单、我喜欢及当日日推。
3. QQ：验证 QQ/微信 SSO 子窗口共享同一 Electron 会话；账号验证和拉歌单错误分开。
4. 酷狗：验证现有 App QR 授权链路及令牌可用性；未通过的接口明确标记为失败。
5. 每个平台记录三个独立状态：登录入口可打开、账号确已验证、歌单和日推确已更新。
6. 不导出真实 Cookie、手机验证码、WebDAV 密码；不能将编译通过当作实测通过。保留 PR #4 为 Draft，不直接合并 main。

**完成标准：** 真实 Windows 主程序至少一条平台路径从登录到歌单读取可用，其他平台逐一记录真实阻塞点和可复现错误。

## 阶段二：体验和本地歌单管理

1. 在原生左侧“我的列表”中实现 Ctrl/Shift 整张歌单选择、选中状态和批量菜单，不改变歌单内现有歌曲多选。
2. 操作按来源分流：
   - 原生歌单：本地归档或删除，由原生 WebDAV 处理同步。
   - 第三方账号镜像：归档或隐藏只改变本地呈现；下次刷新不自动复活；不能回写删除原账号。
   - LX-N 镜像：双向关闭时不写 WebDAV；开启后针对允许的来源操作纳入 LX-N 全库更新。
3. 增加对应平台的“立即刷新”与每日日推刷新，使用稳定的当前推荐歌单标识。
4. 对 LX-N 日推历史采用保守识别：来源和历史身份足够可靠时才自动归档，不应靠模糊名字误伤普通用户歌单。
5. 在设置页区分“账号登录成功”“歌单同步成功”“失败等待重试”，并展示上一次成功时间。

**完成标准：** 数十张歌单能 Ctrl/Shift 多选；外部镜像隐藏后刷新不复活；刷新日推不会无限新建用户歌单；同步失败可见但不阻塞正常界面。

## 阶段三：LX-N WebDAV 写回和最后提交覆盖

1. 基于当前 `packages/shared/app/modules/sync/external/lxWebdav.ts` 的只读导入实现写回通道；双向设置默认关闭。
2. 首次双向同步：以远端 `/LX_Music/playlists.json` 为准，不能让 PC 上残留的旧镜像自动覆盖现有手机数据。
3. 写回范围仅 `data.defaultList`、`data.loveList`、`data.userList` 所代表的 LX-N 完整歌单库；保留 LX 文件中与歌单无关的其它顶层数据与未知字段，不能把简化后的播放器镜像当作完整源数据而丢失音乐元数据。
4. 用户明确选择最后成功提交的整库覆盖，不实现逐歌单自动合并。研究 WebDAV 条件写入 / ETag / 读回校验，避免对并发提交顺序做无法验证的保证。
5. 一旦可信源数据确认删除某歌单，应同步移除其 LX-N 镜像，归档也不保护已经由来源删除的列表。
6. 网络异常、损坏 JSON、鉴权失败不能被视作远端清空；不执行危险的错误传播。
7. 不改动安卓原版 LX-N Music：如果它离线重连时重放操作、反向合并，应标记为已知兼容行为，不能承诺严格按 PC 的最后写入覆盖模型。
8. 按需求没有额外危险确认、没有自动备份。测试时只使用隔离目录和虚构歌单，不在未经验证的功能上直接写用户真实 `playlists.json`。

**完成标准：** 在隔离的 WebDAV 测试环境中，PC 创建、编辑、删除 LX 歌单及手机端变化可按可实现的范围传播；不会触碰 AnySynListen 原生库/网易云/QQ/酷狗；异常输入不清空已有数据。对于未修改的手机 App，严格 LWW 若失败，必须明确披露。

## 阶段四：回归、构建和交付

1. 回归登录、只读镜像、Ctrl/Shift、归档、删除、每日推荐以及三类同步通道的互不干扰。
2. 覆盖测试：首次远端优先、双端离线修改、整库覆盖、删除传播、重复刷新、平台认证过期、格式损坏、网络断开、无权限写入、来源丢失、并发上传。
3. 优先使用现有工作区、直接文件编辑和 GitHub Actions Windows 构建；不要求用户安装完整 Visual Studio C++ 工具链。
4. 测试通过后提供独立的 AnySynListen 测试构建及可读的已通过/未通过列表。
5. 不在用户明确认可前把现有 Draft PR #4 或依赖分支直接合入 main。

## 已知风险和明确不提供的功能

- 严格的手机端“最后写入整库覆盖”在不改安卓 App 的约束下**可能无法完全实现**。这不是编译可以验证的事情。
- 不自动备份、不要求确认时，较晚的错误但有效的用户提交也可能永久覆盖另一端尚未同步的修改；不保证撤销永久删除。
- 普通 WebDAV 无法自然提供多端秒级推送。PC 本地变更可以及时提交；手机是否定期接收及接收速度取决于现有 LX-N 行为，必要时使用它的手动同步按钮。
- 音乐平台只能按实际授权和可用接口读取数据。日推“刷新”不保证每天可以获得多批不同歌曲。
- 不能依据一次暂时为空的 HTTP/API 响应认定来源已经删除全部歌单。

## 与早期交接的差异

`docs/DEVELOPMENT_HANDOFF_zh.md` 是开发状态快照。此后的 Q1～Q24 明确要求：**不要新增危险操作确认、不要自动备份、不修改 LX-N 安卓客户端，LX 冲突采用整库最后成功提交覆盖。** 实施时以本文件和 ADR 的最新产品决策为准，同时沿用交接中的登录方案与凭据安全约束。
